## §3 Input Validation

**PASS.** All four wire schemas enforce strict structural validation via Zod before any
field is accessed:

- Enum fields: `z.enum([...])` — exact string-set enforcement on `Severity`,
  `TestCoverageStatus`, `BlastRadiusNodeKind`, `BlastRadiusRelationship`,
  `AnalysisStage`, `AnalysisStatus`.
- Numeric counter fields: `z.number().int().min(0)` — rejects negative values,
  non-integers, and non-numbers.
- Confidence: `z.number().min(0).max(1)` — rejects values outside 0–1.
- Timestamps: `z.string().datetime()` — strict ISO 8601 with timezone enforcement.
- All four mapper functions (`reviewFromWireFormat`, `intentFromWireFormat`,
  `blastRadiusFromWireFormat`, `metadataFromWireFormat`) accept Zod-typed `*Wire`
  parameters. No mapper function accepts `unknown` or `any`.
- No raw `as unknown as T` assertions on untrusted input appear in any production file.
- Contract SEC-001 is satisfied: the comment on each mapper explicitly directs callers
  to parse via the corresponding `WireSchema` before invoking the mapper.

### sec-001 — Type assertion on static fixture (info / accepted_risk)

**Description:** In TEST-125, two `as { ... }` type assertions are applied to
`blastRadiusFixture`, a statically-imported compile-time JSON file:

```ts
(blastRadiusFixture as { nodes: { id: string }[] }).nodes.map(...)
blastRadiusFixture as { edges: { source: string; target: string }[] }
```

**Why it is not a vulnerability:** `blastRadiusFixture` is imported at build time via
`import ... from "...json"`. It is not runtime-untrusted input — it is a fixture baked
into the test bundle. The assertions do not bypass any trust boundary.

**Recommended action (informational only):** No action required for this feature. If
the test is ever refactored to accept runtime-dynamic fixture input, replace the `as`
assertions with a `BlastRadiusResultWireSchema.parse()` call instead.

**Status:** accepted_risk

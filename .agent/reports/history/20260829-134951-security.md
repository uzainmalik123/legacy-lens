### LOW-001 — `z.string()` fields in `GuardrailTestSchema` have no length constraints

**Severity:** Low  
**Category:** input-validation  
**File:** `lib/analysis/guardrail-test.ts`  
**Lines:** 23–35  

**Description:**  
All string fields in both `GuardrailTestSchema` and `GuardrailTestWireSchema` use bare `z.string()` without minimum or maximum length constraints. The most notable field is `code` (the Java source), which is unbounded. In the current fixture-driven model this is benign: the only source is a static development fixture bundled into the app. However, when Feature 6 replaces the fixture with real Bob API output, an unconstrained `code` field could accept an arbitrarily large response, which could impact memory and rendering performance.

**Evidence:**
```ts
code: z.string(),      // line 29 — no .max() bound
rationale: z.string(), // line 30
```

**Risk context:**  
This is **not exploitable today** — the data source is a static compile-time JSON file, not user input or a live API call. The risk materialises only if Feature 6 introduces a network data path without also adding length constraints.

**Recommended action:**  
When Feature 6 introduces a real API data path, add `z.string().max(N)` constraints to at minimum `code` (e.g. `max(32_000)` characters, matching a reasonable upper bound for a single test class) and `rationale`/`detectionNote` (e.g. `max(2000)`). This is a pre-emptive recommendation for the Feature 6 implementation plan, not a fix required for Feature 5 merge.

### INFO-001 — No Content Security Policy headers configured

**Severity:** Info  
**Category:** configuration  
**File:** `next.config.ts`  
**Line:** 3  

**Description:**  
`next.config.ts` does not configure HTTP security headers (`Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`). This is a pre-existing gap that predates this feature. The application renders user-provided code inside a `<pre>` block; without a restrictive CSP, any future introduction of `dangerouslySetInnerHTML` or a third-party script would not be constrained.

**Evidence:**
```ts
const nextConfig: NextConfig = {
  reactCompiler: true,
  // no headers() configuration
};
```

**Risk context:**  
This is a demo/hackathon application. The code block in `GuardrailTestView` uses plain JSX text interpolation (no `dangerouslySetInnerHTML`), so the absence of CSP does not currently create an exploitable path. However, CSP headers are considered a defence-in-depth baseline for any web application.

**Recommended action:**  
This is a pre-existing configuration gap outside the scope of Feature 5. Track as a follow-up hardening item. For production readiness, add `headers()` to `next.config.ts` with at minimum `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY`.

### INFO-002 — `passthrough()` on wire schemas allows unvalidated extra fields

**Severity:** Info  
**Category:** input-validation  
**File:** `lib/analysis/guardrail-test.ts`  
**Lines:** 52, 69  

**Description:**  
Both `BoundaryScenarioWireSchema` and `GuardrailTestWireSchema` use `.passthrough()`, which allows unknown fields in the wire JSON to flow through the Zod parse without error. This is consistent with the project-wide convention (all four prior wire schemas use the same pattern for `_fixture_note` compatibility). The domain mapper `guardrailTestFromWireFormat` does not propagate unknown fields — only the explicitly mapped camelCase fields reach the UI. Therefore the passthrough is contained: extra fields are parsed-through but discarded at the mapper boundary.

**Evidence:**
```ts
export const GuardrailTestWireSchema = z.object({ ... }).passthrough();
// mapper only maps named fields, not spread/Object.assign of wire
```

**Risk context:**  
No exploitable path. The unknown fields are silently discarded by the mapper. The pattern is intentional and consistent with the project convention.

**Recommended action:**  
No action required for Feature 5. When Feature 6 introduces a live API response path, consider whether `.strict()` should replace `.passthrough()` at the outer schema level to detect API contract drift early. This should be an explicit architectural decision documented in the Feature 6 plan.

### INFO-003 — `navigator.clipboard.writeText` writes fixture-controlled Java code to clipboard

**Severity:** Info  
**Category:** configuration  
**File:** `app/components/GuardrailTestView.tsx`  
**Lines:** 52–60  

**Description:**  
The copy button writes `guardrailTest.code` to the system clipboard. The content of `code` is entirely fixture-controlled (and in the future, Bob-controlled). In a demo context this is the correct and expected behavior. However, the clipboard write is not guarded by a `document.hasFocus()` or user-gesture check beyond the button click itself; browsers enforce a user-gesture requirement automatically. The error path is correctly silenced. No data exfiltration is possible — the clipboard write is one-directional (app → clipboard, not clipboard → app).

**Evidence:**
```ts
navigator.clipboard?.writeText(guardrailTest.code).then(
  () => { ... },
  () => { /* clipboard unavailable — no-op */ }
);
```

**Risk context:**  
This is standard clipboard API usage. The `?.` optional chain guards against `navigator.clipboard` being undefined (e.g. insecure contexts). Errors are silently swallowed as required by REQ-010. No risk.

**Recommended action:**  
No action required. Pattern is correct. For completeness, the `setTimeout` inside the success callback (line 55) runs `setCopyLabel("Copy")` — this does not need cleanup since it only updates local component state and the 2-second duration is short enough that unmount before completion is benign (the state update would be a React no-op in strict mode or trigger a mild warning in development builds). Not a security concern; noted for completeness.

## Detailed Analysis by Category

### Authentication and Authorisation
No routes, API endpoints, server actions, or authentication mechanisms are introduced by this feature. The application is a client-side demo tool with no user sessions. **No findings.**

### Input Validation
All data paths flow through Zod wire schemas before any field is accessed (confirmed in `loader.ts` line 68: `GuardrailTestWireSchema.parse(guardrailTestWireJson)` called before `guardrailTestFromWireFormat`). The `GuardrailTestWireSchema.parse()` call is a hard parse (throws on failure), not `safeParse`, so a malformed fixture would cause a build-time or server-render error rather than silently corrupt data. **One low finding (unbounded string lengths) — not exploitable in current scope.**

### Output Handling (XSS)
- All string fields from `GuardrailTest` are rendered via standard JSX text interpolation (React escapes `<`, `>`, `&`, `"` automatically).
- `guardrailTest.code` is rendered inside `<pre>{guardrailTest.code}</pre>` (line 245) — no `dangerouslySetInnerHTML`. React renders this as a text node, not parsed HTML. **No XSS risk.**
- `guardrailTest.filename`, `behaviorRuleId`, `protectedBehavior`, `detectionNote`, `rationale` — all rendered as text children in JSX. **No XSS risk.**
- Confirmed by grep: zero occurrences of `dangerouslySetInnerHTML` in any changed file.
- The `DiffPane.tsx` `<mark>` pattern (pre-existing, not in scope) also uses React JSX children (text strings passed as `{token}`, `{before}`, `{after}`), not HTML insertion. Not a security concern.

### Injection Risks
- No SQL, shell, template, or LDAP injection paths. No database. No shell command execution. No template rendering outside React JSX. **No findings.**

### SSRF
No outbound HTTP requests are made by any changed file. The `loader.ts` modifications only add a static JSON import. **No findings.**

### Path Traversal
No filesystem access paths are constructed from runtime data. All file imports are static compile-time paths. **No findings.**

### Secret Exposure

- No `process.env` access.

- The fixture JSON contains only domain data (behavior rule IDs, Java code, financial scenario values). None of this is sensitive.

### Dependency Security
No new runtime or devDependencies were added by this feature (`package.json` unchanged). Pre-existing dependencies (Next.js 16.3.3, React 19.2.8, Zod via existing usage) are unchanged. **No findings.**

### Unsafe Configuration
- `tsconfig.json`: `"strict": true` is set. **Pass.**
- `next.config.ts`: No CSP headers (pre-existing gap, see INFO-001). No `dangerouslyAllowSVG`. No wildcard CORS. `reactCompiler: true` unchanged.
- No new middleware or proxy configuration introduced.

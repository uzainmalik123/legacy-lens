## Findings

### SEC-FIND-001 — LOW

**Category:** output-encoding / information-disclosure  
**File:** [`app/api/analyze/route.ts`](app/api/analyze/route.ts), line 32  
**Description:** Filesystem error messages are forwarded to the client.

When `readAllowedSources()` throws (e.g. a file is missing), the route handler
returns `err.message` directly in the JSON response body:

```typescript
const message = err instanceof Error ? err.message : "Unknown error reading source files";
return NextResponse.json({ error: "source_read_failed", message }, { status: 500 });
```

Node.js filesystem errors include the absolute server path in their message
(e.g., `ENOENT: no such file or directory, open '/home/uzi/Projects/hackathons/legacy-lens/demo/...'`).
This leaks the server's working directory to anyone who can trigger the error.

**Evidence:** `route.ts:32` — `const message = err instanceof Error ? err.message : ...`

**Risk context:** Local demo only. No real user has access to trigger this.
In a deployed scenario this would reveal the server's filesystem layout.

**Recommended action:** Replace the raw `err.message` with a static message
(e.g., `"Could not read analysis source files."`) and log the actual error
server-side only. The property to preserve is that specific filesystem details
do not reach the response body.

**Status:** Accepted risk for hackathon local demo.

### SEC-FIND-002 — LOW

**Category:** output-encoding / information-disclosure  
**File:** [`lib/analysis/bob-client.ts`](lib/analysis/bob-client.ts), lines 70–72  
**Description:** Raw Bob API error text (up to 200 characters) is included in
`BobApiError.message` and subsequently forwarded to the client by the route handler.

```typescript
throw new BobApiError(
  `Bob API returned HTTP ${response.status}: ${text.slice(0, 200)}`,
  response.status
);
```

The route handler at `route.ts:47` returns `{ message: err.message }` to the client.
If the Bob API returns an error body that contains internal details (endpoint paths,
model identifiers, internal error codes), those details would reach the browser.

**Evidence:** `bob-client.ts:70–72` + `route.ts:46–49`

**Risk context:** Local demo. The Bob API error body is from a trusted internal service.
In production this pattern would warrant sanitisation.

**Recommended action:** For a production deployment, replace Bob API error body
forwarding with a static message (e.g., `"Bob analysis request failed — see server logs."`)
and log the full error server-side. The property to preserve is that internal API
error details from upstream services do not propagate to client responses.

**Status:** Accepted risk for hackathon local demo.

### SEC-FIND-003 — INFO

**Category:** configuration  
**File:** [`app/api/analyze/route.ts`](app/api/analyze/route.ts)  
**Description:** No authentication or rate-limiting on `POST /api/analyze`.

The endpoint is unauthenticated and accepts unlimited requests. Each request
consumes a Bob API credit. A local browser tab could accidentally trigger multiple
requests (though the client-side button-disable guard reduces this risk).

**Evidence:** No auth check in `route.ts`. Client-side disable guard in `ReviewWorkspace.tsx:112`.

**Risk context:** Local demo with one user. Not a security risk in the stated
deployment model.

**Recommended action:** For any non-local deployment: add a server-side
in-flight guard or rate limiter. The client-side `isAnalyzing` check is
not a security control — it is a UX guard only. The server endpoint itself
should reject concurrent or rapid requests to prevent credential exhaustion.

**Status:** Accepted risk. Noted for future deployment.

### SEC-FIND-004 — INFO

**Category:** configuration  
**File:** `next.config.ts`  
**Description:** No Content Security Policy (CSP) headers configured.

The application has no HTTP security headers configured. For a deployed
application this would allow unrestricted script sources.

**Evidence:** `next.config.ts` has no `headers()` configuration.

**Risk context:** Local demo. No cross-origin threats in `localhost` context.

**Recommended action:** Before any public deployment, add a `headers()` function
in `next.config.ts` returning at minimum `Content-Security-Policy`,
`X-Content-Type-Options`, `X-Frame-Options`, and `Referrer-Policy`.

**Status:** Out of scope for hackathon MVP.

### SEC-FIND-005 — INFO

**Category:** path-traversal (defence-in-depth observation)  
**File:** [`lib/analysis/allowlist.ts`](lib/analysis/allowlist.ts), line 78  
**Description:** No explicit root-boundary assertion after `path.join`.

`absolutePath = path.join(base, relativePath)` is safe because `relativePath`
comes from the hard-coded `ALLOWED_PATHS` constant containing no `..` sequences.
However, there is no programmatic assertion that `absolutePath.startsWith(base)`.
If `ALLOWED_PATHS` were ever modified to include a `..` sequence, no runtime
check would catch the traversal before the file is opened.

**Evidence:** `allowlist.ts:78` — `path.join(base, relativePath)` without startsWith guard.

**Risk context:** Zero practical risk while `ALLOWED_PATHS` remains a compile-time
constant. Would become a risk if the allowlist were made dynamic.

**Recommended action:** Adding `if (!absolutePath.startsWith(base + path.sep)) throw new Error(...)`
before `readFile` would provide defence-in-depth at negligible cost. Not required
for the current implementation.

**Status:** Informational. No action required for current scope.
